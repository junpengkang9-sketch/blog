一个真实的 AI 应用，由六层能力叠起来。每一层都回答三件事：要具备什么能力，解决什么生产问题，用什么技术解决。

Python 工程

AI 后端运行时：让 AI 功能跑在长期运行的服务里

工单系统里工单请求被一个 FastAPI 接口接住，处理进度流式返回页面。

核心能力

  • 异步服务：处理长耗时的模型调用
  • 流式输出：把生成过程逐段推给页面
  • 数据持久化：会话与结果落库
  • 稳定调用：超时、重试、限流

生产问题

  • 一次模型调用要数秒到数十秒，同步阻塞会拖垮服务
  • 批量任务串行处理，耗时随任务数线性增长
  • 模型接口会超时、被限流，没有重试和降级就直接失败
  • 用户等待时毫无反馈，会话与结果重启即丢

技术方案

  • FastAPI 加 Pydantic 提供接口与校验
  • asyncio 并发，用信号量限制并发数
  • SSE 流式返回，数据库保存会话
  • 超时设置、指数退避重试、请求限流

典型应用形态

  • 流式对话服务
  • 批量文档、工单处理任务
  • 带会话历史的 AI 助手后端

核心知识

FastAPIPydantic 校验async并发 · 流式 SSE数据SQLAlchemy · PostgreSQL稳定调用超时 · 重试 · 限流

LLM Application

模型接入层：把模型变成程序能可靠调用的组件

工单系统里模型把工单原文读成分类、优先级、负责人和下一步动作；需要客户信息时，提出工具调用。

核心能力

  • 理解模型的行为边界：概率生成、Token、上下文
  • 结构化输出：用 Schema 约束，校验后重试
  • Tool Calling：模型提出调用，由代码执行

生产问题

  • 同一输入多次调用，输出与格式不稳定
  • 输出是自然语言，程序无法直接使用
  • 模型自己碰不到系统，查不了数据、做不了动作
  • 上下文越长越慢越贵，超出窗口直接失败

技术方案

  • Prompt 分层：角色、规则、示例、上下文
  • JSON Schema 或 Pydantic 约束输出，校验失败带错误重试
  • Function Calling：声明工具，模型提出调用，代码执行
  • LangChain：统一封装模型、Prompt、输出解析与工具

典型应用形态

  • 工单、邮件自动分类
  • 表单与字段抽取
  • 内容审核与风险判定
  • 带查询能力的单轮问答

核心知识

神经网络基础→Transformer→Token 与 Context→Prompt→Structured Output→Tool Calling→LangChain

RAG

企业知识层：让模型基于正确、最新、有权限的证据回答

工单系统里系统先检索该客户的订阅规则和历史工单，再让模型作答。

核心能力

  • 切片（Chunk）：保留来源、版本、权限
  • Embedding：把文本变成向量，用相似度找相近内容
  • 混合检索与重排（Search、Rerank）
  • 带引用的回答，并做检索评估（Eval）

生产问题

  • 模型不知道企业私有知识，只能凭训练数据作答
  • 召回旧版本或错误租户的资料，答案自信却错误
  • 无权限的内容被召回，造成越权泄露
  • 检索准不准没人衡量，问题只能等用户投诉才发现

技术方案

  • Embedding 模型加向量库（Qdrant、pgvector 等）
  • 向量检索加关键词检索，再重排
  • 元数据过滤：租户、版本、权限
  • 固定问题集评估：该找的有没有找到

典型应用形态

  • 产品文档、知识库问答
  • 客服知识助手
  • 合同、制度、规则查询

核心知识

Chunk切片Embedding向量化Search向量 + 关键词Rerank重排Eval检索评估

了解即可

查询改写（Query Rewrite）LlamaIndexLangChain retriever增量索引更新文档解析器

4

Agent

任务执行层：从给出建议，到完成任务

工单系统里Agent 依次查客户、查订阅、看日志，高风险动作停下来等管理员确认。

核心能力

  • 控制循环：反复调用 Tool，直到任务完成
  • 状态：State、Checkpoint、Persistence
  • 工作流与 Agent 的取舍
  • 人工确认与护栏

生产问题

  • 单次问答只能给建议，任务仍要靠人一步步执行
  • 多步任务中途出错，状态丢失，只能从头再来
  • 高风险动作（重置权限、退款）不能由模型自行决定
  • 循环失控：无限调用工具，成本和延迟一起放大

技术方案

  • 循环式执行，每一步保存 Checkpoint
  • 固定流程用 Workflow，动态分支才用 Agent
  • Human-in-the-loop：高风险动作停在确认点
  • LangGraph 等框架提供状态、持久化与人工确认

典型应用形态

  • 工单处理 Agent
  • 运维排障助手
  • 跨系统的业务流程自动化

核心知识

Loop反复调用 ToolState状态Workflow工作流Tool工具设计HITL人工确认LangGraph状态图编排

了解即可

Memory长期记忆ReAct多 Agent 协作OpenAI Agents SDK

MCP

系统连接层：让 Agent 用统一方式接入真实系统

工单系统里Agent 通过统一协议访问 CRM、账单和日志，不再每个系统各写一套对接代码。

核心能力

  • Client / Server 与 Transport：本地 stdio，远程 HTTP
  • Tool 与 Resource：把系统能力封装成 Server
  • Schema：用 JSON Schema 描述工具参数
  • Permission：最小权限、写操作确认、调用日志

生产问题

  • 每个应用对接每个系统，适配代码按 N×M 增长
  • 认证、参数、错误处理在各处重复实现
  • 模型可调用的能力，缺少统一的权限边界与审计

技术方案

  • MCP 协议：Client / Server 架构
  • Server 暴露 Tools 与 Resources，参数用 JSON Schema 描述
  • 本地用 stdio，远程用 Streamable HTTP
  • 最小权限，写操作确认，调用留日志

典型应用形态

  • CRM、工单、数据库的 MCP Server
  • 多个 AI 应用共用同一批工具
  • 桌面助手、IDE 接入内部系统

核心知识

Client / Server角色Tool工具Resource资源Schema参数描述Transportstdio · HTTPPermission权限

了解即可

JSON-RPCOAuthPromptsFastMCPMCP Inspector

和 Tool Calling 的关系：Tool Calling 是模型提出调用的能力，MCP 是让这些工具用统一方式接入系统的协议。两者是配合关系，不是替代关系。

版本提示：MCP 规范仍在演进，当前最新版是 2026-07-28，协议核心改成了无状态，去掉了会话与初始化握手。旧教程里的 HTTP+SSE 传输和会话相关写法可能已经过时，以官方规范为准。

Production

生产保障层：让 AI 应用可评测、可追踪、可回归

工单系统里这次处理是否正确，由评测和 trace 给出证据。

核心能力

  • 评测：固定数据集与上线线
  • 追踪与版本：每次运行有 trace，Prompt 与模型有版本
  • 成本、延迟与可靠性：监控、降级、兜底
  • 安全：数据脱敏、Prompt Injection 防护

生产问题

  • 改一次 Prompt 或换模型，不知道整体是变好还是变差
  • Agent 出错后，无法定位是哪一步、哪个工具
  • 延迟、成本没有归因；接口故障时也没有降级方案
  • 用户输入或检索内容里的恶意指令，可能诱导模型越权

技术方案

  • Golden dataset 加回归评测，放进 CI 作为上线门禁
  • Trace 与 OpenTelemetry，可用 Langfuse 等工具查看
  • Prompt、模型、索引版本化，可灰度、可回滚
  • 降级与兜底；输入输出过滤、数据脱敏

典型应用形态

  • 上线前的回归评测门禁
  • 线上运行的 trace 与告警
  • 版本对比与灰度发布

核心知识

Eval评测TraceOpenTelemetry · LangfuseVersion版本Cost & Latency成本与延迟Reliability降级与兜底Security注入防护 · 数据脱敏

合起来：一个 AI 生产系统的全景

六层在同一个系统里的位置

生产就绪的三个问题

  1. 它答对了吗？用评测集回答，不靠感觉。
  2. 它做错时，错在哪一步？用 trace 回答，定位到具体的调用。
  3. 它能碰哪些系统，不能碰哪些？用最小权限和人工确认回答。

不是放弃前端，而是把已有的工程能力，继续延伸到后端、模型、企业知识、工具连接和上线体系。
